01для UX/UI дизайнера, який робить дизайн у коді з Claude

Дизайн у коді з Claude: працюємо вдвох і не ламаємо одне одного

Ти вже робиш дизайн у коді: кажеш Claude, що потрібно, він пише код, ти дивишся результат у браузері. Далі — як організувати це на двох і більше людей: один репозиторій на GitHub, гілка на кожну задачу і Pull Request замість «скинув файл у чат». Плюс тренувальний проєкт, на якому можна все спробувати без ризику.

репозиторійОдин. Екрани, компоненти й токени лежать разом, але в різних папках із чіткими межами.
гілкиОдна задача = одна гілка = один Pull Request. Гілка живе 1–3 дні і зникає після злиття в main.
claudeТвої руки в коді. Git-команди він виконує сам, правила читає з файлу CLAUDE.md у репозиторії.

Усе це ти вже робив у Figma — просто називається інакше

Кілька слів, яких вистачить на всю презентацію і на роботу далі. Лівий стовпчик — те, що ти знаєш. Правий — як це називається в коді та на GitHub.

03три питання, три відповіді

Що тебе турбувало — і що ми з цим робимо

Жодне з питань не вимагає нової інфраструктури. Досить домовленостей, кількох файлів у репозиторії і галочок у налаштуваннях GitHub.

питання 1Чи треба розділяти продукт, компоненти й дизайн-систему на різні репозиторії?
ніОдин репозиторій, три папки: tokens → components → screens. Окремий репозиторій для дизайн-системи — це як окремий Figma-файл бібліотеки: кожну зміну треба публікувати, а в продукті приймати оновлення. Для маленької команди це подвійна робота.
питання 2Як контролювати зміни?
PRmain захищений. Кожна зміна: гілка → Pull Request → перевірка колегою → злиття. У PR лишається історія: хто, що, чому, зі скриншотами «до / після». Плюс автоматична перевірка «проєкт збирається».
питання 3Як зміна спільного компонента не зламає інші екрани?
ds/Спільний код змінюємо окремим маленьким PR у гілці ds/ (design system), який перевіряють обидва. Правило: додавай варіант, не змінюй дефолт. Перевірка — екран #/ui-kit, де видно всі компоненти в усіх станах.

Один репозиторій, три шари, стрілки тільки вниз

05git·гілки

Так виглядає наш приклад у часі: ти у feat/dashboard-redesign, колега у feat/settings-notifications, і одна коротка гілка ds/button-size-sm для спільної кнопки. Колега — другий дизайнер або розробник, правила однакові.

06claude·що казати і що він знає сам

Ти описуєш задачу словами, Claude виконує git і пише код. Праворуч — файл CLAUDE.md у корені репозиторію: правила, які він читає на старті кожної сесії. Тобі не треба їх повторювати.

# Правила для Claude у цьому репозиторії

## Архітектура
- Імпорти тільки вниз: screens → components → tokens
- Стилі тільки через var(--…). Немає токена — запропонуй
  окрему гілку ds/tokens-…
- Компонент для одного екрана — у screens/<екран>/components/
- Кожен варіант спільного компонента — на #/ui-kit

## Гілки і PR
- Ніколи не коміть у main. Нова задача = нова гілка від свіжого main
- feat/<екран>-<що> · ds/<компонент>-<що> · fix/<що>
- У гілці feat/* не змінюй src/components і src/tokens.
  Потрібно — зупинись і запропонуй окрему гілку ds/*
- Новий проп або токен — з дефолтом, який зберігає поточний вигляд
- Breaking change — спитай, знайди всі використання, онови в тому ж PR
- Перед push і PR: npm run typecheck && npm run build
- Не роби force push. Не зливай PR сам — merge робить людина
- Конфлікт: покажи обидві версії простими словами і спитай

  1. main завжди робочий. Напряму в нього ніхто не пушить — GitHub це блокує, Claude це знає.
  2. Одна задача = одна гілка = один PR. «Заодно поправив ще…» — окремий PR.
  3. PR маленький. До ~300 рядків, опис і скриншоти «до / після». Великий PR ніхто не читає уважно.
  4. Екрани схвалює (Approve) другий учасник. tokens і components — обидва: файл CODEOWNERS у репозиторії сам додає другого ревʼюером.
  5. Зелений check «build» обовʼязковий. Проєкт не збирається — PR не зливається. Це страховка від «у мене працювало».

  7. Спільний код — окремий PR, а не частина PR екрана. Тоді його можна злити за 15 хвилин, не чекаючи весь екран.
  8. Ревʼю — протягом робочого дня. Маленький ds/ PR — за 15 хвилин, бо на нього чекає інша гілка.
08src/components·src/tokens

Спільний компонент: додавай варіант, не змінюй дефолт

10крок 3 детально·Button

Кнопка: два шляхи до меншої кнопки

Однакова мета, різниця в одній гілці. Ліворуч — як ламаються чужі екрани. Праворуч — як ми домовились робити. Якщо попросиш Claude піти лівим шляхом, він зупиниться і запропонує правий — так написано в CLAUDE.md.

Правлю Button у гілці Dashboard
  1. У feat/dashboard-redesign просиш «зроби кнопки на Dashboard меншими». Claude без правил зменшив би padding у .button — на Dashboard стало добре.
  2. PR Dashboard великий: 40 файлів, серед них Button.module.css. Ревʼюер дивиться на екран, не на кнопку.
  3. PR злитий. Усі кнопки в Settings — і на решті екранів — стали меншими.
  4. Колега дізнається після релізу: у його PR цих файлів не було, у його гілці кнопки були нормальні.
Спільний код змінився «за компанію». Ніхто не перевірив інші екрани, бо ніхто не знав, що треба. У Figma це — поправити main component і не подивитись на інші сторінки.
Окремий PR ds/button-size-sm
  1. «Закоміть поточне в feat/dashboard-redesign. Почни гілку ds/button-size-sm від свіжого main».
  2. «Додай у Button проп size з дефолтом md і варіант sm. .md не чіпай. Покажи варіант на #/ui-kit».
  3. PR #12: 3 файли, скриншот #/ui-kit, зелений check. CODEOWNERS додає колегу ревʼюером. 15 хвилин → Approve → Squash and merge.
  4. Обоє: «підтягни main». Dashboard пише <Button size="sm">. Settings не змінився.
Зміна спільного коду маленька, видима і перевірена тим, чиї екрани вона могла зачепити. У Figma це — новий variant у бібліотеці й publish.
11конфлікти·і що казати Claude

Конфлікти трапляються рідко і лікуються за 5 хвилин

Конфлікт — це лише коли ви обоє змінили ті самі рядки одного файлу. Різні екрани в різних папках цього не дають. Типові місця: src/App.tsx, components/index.ts, файли токенів.

Якщо Claude каже «конфлікт»
Підтягни main у мою гілку

Claude: «У src/App.tsx конфлікт. У твоїй гілці назва Nimbus Cloud, у main — Nimbus Pro. Яку лишити?» Ти обираєш — він завершує злиття і пушить. Під капотом:

git merge main                 # git пише CONFLICT і назву файлу
# обрати версію рядка → зберегти
git add -A && git commit       # завершити злиття
git push

Не впевнений, що обрати — поклич колегу, це 5 хвилин. Профілактика: маленькі PR, щоденне «підтягни main», спільний код окремими PR.

12тренувальний проєкт·Nimbus

Проєкт, на якому можна все зламати і нічого не втратити

У цьому ж репозиторії — маленький застосунок у стилі GitHub Dark із тією самою архітектурою: три екрани, пʼять спільних компонентів, токени. Унизу кожного екрана — підказка, де лежить його код і як назвати гілку. Вправи — у PRACTICE.md, на 1–2 години вдвох: A і B — двоє учасників, наприклад ти і другий дизайнер.

Перейменувати проп і нікого не зламати.Домовитись у чаті → ds/ → знайти всі використання → оновити в тому ж PR → ревʼю обох.
13далі

Що розробник налаштує один раз, і чого ми свідомо не робимо

Уся «інфраструктура» — чотири файли в репозиторії і кілька галочок у налаштуваннях GitHub. Решта — домовленості, які Claude тримає за нас.

Налаштувати один раз · розробник
  • Settings → Rules → ruleset для main: Require a pull request (1 approval) · Require review from Code Owners · Require status checks: build · Block force pushes.
  • Settings → General → Pull Requests: лише Allow squash merging, увімкнути Automatically delete head branches.
  • Вписати реальні GitHub-логіни в .github/CODEOWNERS.
  • За бажанням: Settings → Pages → Deploy from a branch → main / docs — ця презентація відкриється за посиланням.
