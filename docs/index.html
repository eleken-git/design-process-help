Як просити Claude

Добрий запит має чотири частини. Усі запити на цій карті зібрані за цією формулою і написані англійською: копіюйте їх і підставляйте своє замість [дужок].

Що

«Check» або «Build», і що саме

Де

Сторінка, компонент або ширина екрана

Доказ

Скріншот, таблиця, вивід команди або тест

Далі

«Wait for my OK» або «Fix it right away»

прикладCheck keyboard navigation on the settings page, show a screenshot of the focus on every button and wait for my OK before fixing.

Спочатку звіт

Ви бачите проблеми до того, як змінюється код, і самі вирішуєте, що виправляти. Дозвіл дає ваше OK.

Доказ замість слова «готово»

Скріншот, вивід команди або зелений тест. Фраза «я перевірив» доказом не є.

Закріпіть тестом

Попросіть Playwright-тест, і ту саму перевірку можна повторити однією командою.

1

Межі проєкту

scope

Список того, що ви робите, і того, чого не робите. Його пишуть до коду, щоб «маленька правочка» не тягнулася три місяці.

Що перевірити

  • Список сторінок і функцій
  • Що входить і що ні
  • Хто дає тексти й фото
  • Скільки кіл правок
  • Хто публікує сайт

Скажіть Claude

Create a SCOPE.md for this project: the list of pages and features, what is in scope and what is out of scope (backend, CMS, domain, hosting, SEO strategy, copywriting, analytics, maintenance). Mark anything I have not decided yet as a "question for the client".

Навіщо: кожен пункт із правої колонки колись попросять. Коли він записаний, розмова про нього займає хвилину.

2

Що дати Claude на старті

brief

Claude будує з того, що ви дали. Чого бракує в матеріалах, він домальовує сам, і часто не так, як ви задумали.

Що перевірити

  • Кадр Figma для кожного екрана
  • Токени замість «на око»
  • Найдовше ім'я і порожній список
  • Поведінка між брейкпоінтами
  • Анімації: що, коли, скільки мс
  • AGENTS.md у репозиторії

Скажіть Claude

Here is the design: [Figma link]. Before writing any code, list what you are missing: states, tablet behavior, copy, photos, and tokens that do not exist in our token set. Do not make anything up; ask me questions.

Перевірте самі: якщо Claude не поставив жодного питання до складного екрана, попросіть його перелічити, що він припустив сам.

3

Семантика

semantic HTML

Кожен блок сторінки названо за змістом: шапка, меню, головне, підвал. За цими назвами сторінку розуміють браузер, пошуковик і програма читання з екрана.

Що перевірити

  • header, nav, main, footer
  • Один h1 на сторінку
  • Заголовки без стрибків: після h2 не h4
  • button для дії
  • a для переходу
  • Розмір шрифту задає CSS, а не рівень заголовка

Скажіть Claude

Check the markup of the [page name] page: does it have header, nav, main and footer; is there exactly one h1 and do the headings go in order without skipping levels; are actions built with button and navigation with a? First show me the heading tree and a plain-language list of problems.

Перевірте самі: дерево заголовків має читатися як зміст книжки.

Блок div сам по собі нормальний. Погано, коли з div зроблено все, навіть кнопки.

4

Доступність

accessibility, WCAG

Сайтом користуються люди, які не бачать екран, не тримають мишку або погано розрізняють кольори. Більшість проблем знімає правильна розмітка і кілька правил дизайну.

Що перевірити

  • Уся сторінка проходиться клавішею Tab
  • Фокус видно
  • alt у змістовних картинок
  • label у кожного поля
  • Контраст 4.5 : 1 і 3 : 1
  • Помилку описано словами, не лише червоним
  • lang="uk" у html
  • Посилання «Перейти до змісту»
  • Зона натиску від 24 × 24 px
  • Анімації вимикаються через prefers-reduced-motion
  • Збільшення до 200% без поломок

Скажіть Claude

Run an accessibility audit of the [page name] page. Go through it with the keyboard and check visible focus, alt text on images, labels on form fields, text contrast (4.5:1) and icon contrast (3:1), the lang attribute on html, and error messages. Run axe through Playwright. List the problems from most to least important and add a screenshot of the focus state on every interactive element. Wait for my OK before fixing anything.

Перевірте самі: натисніть Tab кілька разів. Якщо не видно, де ви зараз, це баг. На Mac Cmd + F5 вмикає VoiceOver: послухайте свою сторінку хвилину.

Автоматична перевірка знаходить лише частину проблем, тому клавіатуру й читач екрана перевіряють руками. ARIA додають там, де звичайного HTML не вистачає; спершу беруть правильний тег.

5

Адаптивність

responsive

Сайт має добре виглядати на будь-якій ширині, зокрема між вашими макетами. Брейкпоінт (ширину, на якій верстка перебудовується) ставлять там, де вона починає ламатися. Підганяти його під конкретну модель телефона не треба.

Що перевірити

  • 320 px без горизонтального скролу
  • Плавно тягнути вікно від 320 до 1920
  • Довгі слова й кнопки не вилазять
  • Картинки не розтягуються
  • Меню на телефоні
  • flex, grid, max-width, clamp() замість сотень px

Скажіть Claude

Take screenshots of the [page name] page at 320, 375, 390, 768, 1024, 1280, 1440 and 1920 px. Find horizontal scrolling, text that overflows its container, and places where the layout breaks between these widths. Suggest breakpoints where the layout actually breaks, not for specific devices.

Перевірте самі: у Chrome відкрийте DevTools, натисніть Cmd + Shift + M і повільно тягніть край екрана.

320 px узято з WCAG (критерій Reflow): на такій ширині контент читається без горизонтального скролу.

6

Стани

UI states

Кожен елемент має кілька станів. Стан, якого немає в макеті, Claude придумає сам, тому краще показати йому всі.

Що перевірити

  • hover, focus, active
  • disabled, loading
  • Порожній список
  • Помилка завантаження
  • Найдовший текст
  • Форма: відправка, успіх, помилка

Скажіть Claude

Find every interactive element on the [page name] page and check the hover, focus, active, disabled and loading states, plus the empty and error states for lists and forms. Show me a grid of screenshots and a list of missing states. For each missing state, propose a design using our tokens.

У Nimbus усі варіанти компонентів зібрані на #/ui-kit. Новий стан потрапляє туди в тому самому PR.

7

Порядок у коді

maintainability

Після вас цей код відкриє інша людина. Зрозумілі назви і папки заощадять їй дні.

Що перевірити

  • Назви за змістом
  • Один компонент, одна задача
  • Кольори й відступи з токенів
  • Повтор без фанатизму
  • Без мертвого коду і console.log

Скажіть Claude

Review the folder structure and naming in src. Find unclear names (like Component1 or getData2), duplicates, raw color values instead of tokens, and dead code. Explain in plain language what should be fixed before handoff and what can stay.

Два схожі шматки коду ще не привід робити універсальний компонент на 14 props.

8

Сценарії і форми

functional QA

Пройдіть сайт як відвідувач: клацніть усе, заповніть кожну форму неправильно, натисніть «Назад».

Що перевірити

  • Логотип веде на головну
  • Усі посилання і якорі
  • Кнопка «Назад» у браузері
  • Сторінка 404 з виходом
  • Форми: порожня, неправильна, успіх, помилка
  • Куди приходять листи з форм

Скажіть Claude

Write Playwright tests that go through the site like a visitor: click the logo, the menu and every link, open a URL that does not exist (expect a 404), and submit every form empty, with an invalid email, and filled in correctly. Run them and explain in plain language what failed.

Перевірка форми в браузері допомагає людині не помилитися. Зловмисника вона не зупинить: дані захищає сервер, тобто бекенд.

9

Браузери

cross-browser

Ваш Chrome не єдиний браузер. Найчастіше сюрпризи дає Safari, особливо на iPhone.

Що перевірити

  • Chrome
  • Safari на Mac та iPhone
  • Firefox
  • Edge
  • Шрифти, sticky, відео
  • Поля дати і select

Скажіть Claude

Run our Playwright tests in three engines: Chromium, WebKit (the Safari engine) and Firefox. Take screenshots of the main pages in each one and show me where they differ.

Перевірте самі: WebKit у Playwright близький до Safari, але п'ять хвилин на справжньому iPhone він не замінить.

10

Швидкість

performance, Core Web Vitals

Сторінка має з'являтися швидко і не стрибати під пальцем. Найчастіше її гальмують важкі картинки.

Що перевірити

  • WebP або AVIF
  • Картинки під ширину екрана
  • lazy loading нижче першого екрана
  • width і height у картинок
  • Лише потрібні шрифти
  • Сторонні скрипти: тільки потрібні
  • Стиснення Gzip або Brotli

Скажіть Claude

Check the performance of the [page name] page: run Lighthouse, find images over 300 KB, images without width and height, and unnecessary fonts and third-party scripts. Report LCP, CLS and TBT (Lighthouse does not measure INP; TBT is the closest lab metric) and tell me what to fix first.

Це цілі якості. Не обіцяйте клієнту Lighthouse 100/100 на кожній сторінці.

11

Пошук і запуск

SEO baseline, launch

Так сайт виглядає в пошуку, у вкладці та в месенджері, коли ним діляться. Це теж ваш дизайн.

Що перевірити

  • Свій title на кожній сторінці
  • meta description
  • Один h1
  • favicon та іконка для телефона
  • Картинка для поширення (Open Graph), якщо в scope
  • Сторінка 404
  • robots.txt і sitemap.xml
  • HTTPS і редирект з http
  • canonical, якщо є дублі сторінок

Скажіть Claude

Check every page before launch: title and meta description (unique on each page, not empty), a single h1, lang, favicon, social sharing image, 404 page, robots.txt, sitemap.xml, HTTPS and the redirect from http. Give me a table: page, what is there, what is missing.

Перевірте самі: надішліть посилання на сайт собі в месенджер і подивіться на картку.

12

Чиста збірка

build, console

Перед здачею проєкт має зібратися з нуля без помилок, а консоль браузера має мовчати.

Що перевірити

  • npm install з нуля
  • npm run build без помилок
  • lint і тести зелені
  • Консоль без помилок
  • Без тестових даних і console.log

Скажіть Claude

Clone the project into a clean folder and run npm install, npm run build, lint and the tests. Then open every page and collect the errors and warnings from the browser console. Show me what failed and wait for my OK before fixing it.

У репозиторії design-process-help перед кожним PR запускають npm run typecheck && npm run build.

13

Репозиторій і README

repository, README, .env.example

Клієнт має отримати репозиторій, який інша людина запустить без дзвінка вам. Архів website-final.zip для цього не годиться.

Що перевірити

  • Репозиторій на GitHub, GitLab або Bitbucket
  • README з кроками запуску
  • .env.example без значень
  • Секретів немає і в історії git
  • Гілка main чиста

Скажіть Claude

Prepare the repository for handoff. Check that .env, node_modules, .DS_Store and any keys are not in git, including the history. Create .env.example with the variable names and no values. Write a README with requirements, installation, running, building and environment variables. Then follow the README steps in a clean folder and tell me whether everything started.

Якщо ключ колись потрапив у git, видалити файл замало: ключ треба замінити на новий у сервісі, який його видав.

14

Доступи і власність

ownership, access

Домен, хостинг і аналітика мають належати клієнту. У документі пишуть, хто власник і де увійти. Паролі туди не пишуть ніколи.

Що перевірити

  • Власник кожного сервісу
  • Адреса входу
  • Хто продовжує оплату
  • Паролі передано окремо
  • Ваші доступи після здачі погоджено

Скажіть Claude

Write the "Access" section of HANDOVER.md: a table of the project's services (domain, hosting, repository, analytics, form email, third-party integrations) with the columns owner, sign-in URL and who pays for renewal. Do not write passwords, keys or recovery codes; mark them as "shared separately".

15

Інструкції для клієнта

handover docs

Покажіть клієнту, як самому змінити текст і фото, щоб дрібні правки не йшли через вас.

Що перевірити

  • Адреса сайту і дата здачі
  • Список сторінок і функцій
  • Де лежать логотипи, фото, тексти
  • Як змінити текст
  • Як замінити фото
  • Шрифти й фото з окремою ліцензією
  • Рішення: пункти меню, адресат форм, мови

Скажіть Claude

Write a client-facing section of HANDOVER.md called "What was delivered and how to edit it": the site URL, the handoff date, the list of pages and features, where the source files live, step-by-step instructions for "edit text" and "replace a photo" (format, aspect ratio, size), and the fonts and photos that have separate licenses. Keep it simple and free of jargon, and walk through one edit from start to finish.

16

Підтримка і прийняття

support, sign-off

Домовтеся, що вважається помилкою, а що новою роботою. Потім попросіть клієнта письмово підтвердити, що він отримав усе зі списку.

Що перевірити

  • Канал підтримки і строк
  • Що писати в запиті: сторінка, пристрій, скріншот
  • Відкриті питання: власник, крок, дата
  • Відомі обмеження
  • Про безпеку й бекапи лише після перевірки
  • Підтвердження прийняття

Скажіть Claude

Верстак

Верстак тримає деталь рівно, щоб кожен різ виходив однаково. Харнес робить те саме для Claude: правила, пам'ять у файлах, скіли й перевірки, з якими ви починаєте будь-який клієнтський проєкт.

Тут зібрано практики п'ятьох інженерів, адаптовані під дизайнера, який здає фронтенд клієнту.

Що таке харнес

Агент складається з моделі й харнесу. Цю формулу Viv Trivedy наводить Addy Osmani: харнес охоплює все, що не є самою моделлю. Модель ви не змінюєте. Харнес змінюєте щодня.

Зберіть верстак за шість запитів

Один раз, у новому порожньому репозиторії. Потім кожен клієнтський проєкт починається з цього шаблону.

  1. 1

    Каркас шаблону

    Create a template repository called verstak for frontend client projects. Add this structure: AGENTS.md, CLAUDE.md (one line that imports AGENTS.md), PROJECT.md, DESIGN.md, FRONTEND.md, HANDOFF.md, PROMPT_plan.md, PROMPT_build.md, specs/pages, specs/features, plan/IMPLEMENTATION_PLAN.md, plan/progress.md, .claude/skills, .claude/settings.json, tests/accessibility, tests/visual, tests/e2e and README.md. Fill each file with a short template and a comment on what goes there. Do not add any client-specific content.

  2. 2

    AGENTS.md

    Write AGENTS.md for this template. Keep it under 60 lines, like a pilot's checklist: the commands (dev, build, lint, typecheck, test:e2e), the folder structure, and hard rules (styles come from tokens only, button for actions and a for navigation, one task per session, never commit to main, run every quality gate before saying done). Every rule must be something I can check.

  3. 3

    FRONTEND.md зі стандартом якості

    Write FRONTEND.md as our quality standard. Cover these areas: semantic HTML, accessibility (WCAG 2.2 AA basics), responsive layout from 320 px, UI states, maintainable code, performance (Core Web Vitals), browsers, SEO basics and a clean build. For each area, write three to six short rules that can be checked, and name the command or test that verifies each one.

    Зміст для цього файлу вже є: 16 зупинок із вкладки «Карта фронтенду».

  4. 4

    Запити для планування і будування

    Write PROMPT_plan.md and PROMPT_build.md. Plan mode: read AGENTS.md, PROJECT.md, DESIGN.md, FRONTEND.md and specs/, compare them with src/, and write a prioritized list of small tasks to plan/IMPLEMENTATION_PLAN.md; plan only, do not implement anything. Build mode: read plan/progress.md first, pick the single most important task, implement it, run every quality gate, commit only when they pass, then update the plan and plan/progress.md.

  5. 5

    Ворота якості і hook

    Set up the quality gates: npm scripts for lint (with jsx-a11y rules), typecheck, build and test:e2e; Playwright tests with axe for accessibility, screenshots at 320, 375, 768, 1024, 1440 and 1920 px, a console-error check and a broken-link check. Add a Stop hook in .claude/settings.json that runs typecheck and lint and sends any failure back to you. Then make each gate fail once on purpose and show me the output, so I know it works.

  6. 6

    Три скіли

    Use skill-creator to create three skills in .claude/skills: build-page (turns a spec from specs/pages into a page that uses our tokens), frontend-qa (runs every quality gate and reports problems in plain English with screenshots, most important first) and client-handoff (prepares README, .env.example and HANDOFF.md). None of them may fix, publish or merge anything without my OK.

    Більше ідей для скілів є на першій вкладці, у розділі «Перевірки, які варто перетворити на скіли».
