Будуємо харнес

Харнес — це все, що стоїть навколо AI-агента і робить його передбачуваним: файл із правилами, який він читає на старті, домовленість «спершу опис, потім код», тест перед виправленням, навички, що спрацьовують самі. Без харнесу агент — балакучий чат. З харнесом — колега, який працює за твоїми правилами.

Нижче чотири матеріали, на яких побудований і цей репозиторій. Кожен описаний простими словами: що це, головне і що з нього брати нам. Оригінали англійською, читати їх не обовʼязково.

LLM Wiki: агент сам веде базу знань

Що це

Коротка ідея-нотатка, яку автор пропонує просто скинути своєму агенту. Звична робота з документами виглядає так: завантажив файли, поставив питання, модель шукає шматки і відповідає. Щоразу з нуля, нічого не накопичується. Карпаті пропонує інакше: агент веде вікі — набір звʼязаних markdown-сторінок, які він сам пише і оновлює з кожним новим джерелом. Ти читаєш, він пише.

Головне

  • Три шари: сирі джерела (їх ніхто не змінює), вікі (її пише тільки агент) і схема — файл правил на кшталт CLAUDE.md, який пояснює агенту, як вікі влаштована і що робити.
  • Три дії: додати джерело (агент читає, обговорює з тобою і оновлює 10–15 сторінок), запитати (гарну відповідь підшити у вікі як нову сторінку) і перевірити (суперечності, застарілі факти, сторінки без посилань).
  • Два службові файли замість пошукової інфраструктури: index.md — каталог усього, log.md — хроніка змін.
  • Людина курує джерела і ставить питання. Агент робить бухгалтерію, через яку люди кидають вікі: перехресні посилання, оновлення, узгодженість.

Для нас. Наш CLAUDE.md — це та сама «схема»: правила, які агент виконує без нагадувань. І та сама логіка поділу: людина — рішення і смак, агент — рутина.

Kyrylo Genkov · genkovich/sdd

SDD: від ідеї до злитого PR по прямій лінії

Що це

Плагін для Claude Code з 23 навичками, які ведуть фічу від одного речення до перевіреного коду в PR. Кроки йдуть по прямій: описати → уточнити → спроєктувати → розбити на задачі → реалізувати → перевірити → відправити. Кожен крок пише файл, який читає наступний, і відмовляється працювати, якщо попереднього файла немає. Пропустити щось випадково не вийде.

Головне

  • Навички сократичні: ставлять питання і йдуть з тобою по рішеннях, а не вивалюють стіну тексту. Глибина розпитувань налаштовується: easy, medium, hard.
  • Для інтерфейсів є окремий дизайн-конвеєр: design-system (канон: токени, компоненти, інструмент), ux-flows (потоки користувача) і screens — кожен екран у кожному стані: звичайний, завантаження, порожній, помилка.
  • implement працює через TDD: спочатку тест, який падає, потім мінімальний код, перевірка, коміт на кожну задачу.
  • review — незалежна перевірка всієї зміни проти опису. ship запускає фічу по-справжньому, пише changelog і відкриває PR. Злиття в main лишається за людиною.
  • Утиліти на будь-який момент: словник термінів, розбір бага (відтворити → тест → мінімальне виправлення), дорожня карта.

Для нас. Це доросла версія того, що ми робимо руками: спершу домовитися, що будуємо, потім код. «Екран у всіх станах» — саме те, що дизайнер має описати до того, як з'явиться перший рядок.

GitHub · github/spec-kit

Spec Kit: специфікація, яка стає кодом

Що це

Відкритий інструментарій від GitHub для роботи з будь-яким AI-агентом (понад 30 підтримуваних). Головна думка: десятиліттями код був головним, а описи — тимчасовими риштуваннями. Spec Kit перевертає це: специфікація стає виконуваною, з неї народжуються план, задачі і код.

Головне

  • Кроки: constitution — принципи проєкту, один раз; specify — що і навіщо, без технологій; plan — як, з технологіями; tasks; implement; converge — звірити код з описом і додати задачі на те, чого не вистачає. Повторювати, доки не «зійшлося».
  • Розширення для типових ситуацій: bug (оцінити → виправити → перевірити) і assess — оцінка ідеї до коду: збір → дослідження → визначення → варіанти → рішення «робимо / уточнити / не робимо».
  • Налаштування під команду: extensions додають нові команди, presets змінюють формат і термінологію (аж до іншої мови), bundles збирають готовий набір під роль: продакт, аналітик, безпека, розробник.
  • Філософія: намір і «що» раніше за «як»; уточнення кількома кроками замість одного великого промпта.

Для нас. Constitution — це наш CLAUDE.md. Assess — спосіб не будувати те, що не потрібне. Converge — звірити результат з домовленістю, а не з відчуттям «начебто готово».

Jesse Vincent, Prime Radiant · obra/superpowers

Superpowers: навички, які спрацьовують самі

Що це

Методологія розробки для агентів у вигляді набору навичок. Щойно агент бачить, що ти щось будуєш, він не кидається писати код: спершу питає, що ти насправді хочеш, показує дизайн частинами, які можна прочитати, і лише після твого «так» складає план і береться за роботу. Навички вмикаються автоматично, нічого спеціально викликати не треба.

Головне

  • Базовий цикл: brainstorming (уточнити ідею) → окрема гілка → план, написаний так, щоб його виконав «завзятий джуніор без смаку і контексту»: точні файли, код, перевірки → окремий субагент на кожну задачу з двоетапним ревʼю → TDD: тест падає, мінімальний код, тест проходить → ревʼю → злиття або PR.
  • systematic-debugging: чотири фази і залізне правило «без кореневої причини — без виправлень». Три невдалі спроби поспіль означають, що проблема в архітектурі, а не в рядку коду.
  • verification-before-completion: спершу докази, потім слово «готово».
  • Філософія: тести спершу, процес замість вгадування, простота як мета, докази замість заяв.

Для нас. Саме ці навички працюють у цьому репозиторії: брейншторм перед лого, системний пошук причини, коли зникала музика. Це відповідь на питання «чому Claude питає, а не робить одразу».
