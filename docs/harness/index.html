Харнес

Харнес — усе, що стоїть навколо Claude і робить його передбачуваним: правила, пам'ять у файлах, скіли й перевірки. Верстак — ваш шаблон-репозиторій, у якому харнес уже зібраний: з нього починається кожен клієнтський проєкт.

Тут практики п'ятьох інженерів, адаптовані під дизайнера, який здає фронтенд клієнту.

Мова файлів

Файли, які читає Claude (AGENTS.md, FRONTEND.md, PROMPT_*.md, скіли), пишемо англійською, як і запити. HANDOFF.md пишемо мовою клієнта.

Зберіть верстак за шість запитів

Один раз, у новому порожньому репозиторії. Потім кожен клієнтський проєкт починається з цього шаблону.

  1. 1

    Каркас шаблону

    Create a template repository called verstak for frontend client projects. Add this structure: AGENTS.md, CLAUDE.md (one line that imports AGENTS.md), PROJECT.md, DESIGN.md, FRONTEND.md, HANDOFF.md, PROMPT_plan.md, PROMPT_build.md, specs/pages, specs/features, plan/IMPLEMENTATION_PLAN.md, plan/progress.md, .claude/skills, .claude/settings.json, tests/accessibility, tests/visual, tests/e2e and README.md. Fill each file with a short template and a comment on what goes there. Do not add any client-specific content.

  2. 2

    AGENTS.md

    Write AGENTS.md for this template. Keep it under 60 lines, like a pilot's checklist: the commands (dev, build, lint, typecheck, test:e2e), the folder structure, and hard rules (styles come from tokens only, button for actions and a for navigation, one task per session, never commit to main, run every quality gate before saying done). Every rule must be something I can check.

  3. 3

    FRONTEND.md зі стандартом якості

    Write FRONTEND.md as our quality standard. Cover these areas: semantic HTML, accessibility (WCAG 2.2 AA basics), responsive layout from 320 px, UI states, maintainable code, performance (Core Web Vitals), browsers, SEO basics and a clean build. For each area, write three to six short rules that can be checked, and name the command or test that verifies each one.

    Зміст для цього файлу вже є: 16 зупинок на сторінці «Карта фронтенду».

  4. 4

    Запити для планування і будування

    Write PROMPT_plan.md and PROMPT_build.md. Plan mode: read AGENTS.md, PROJECT.md, DESIGN.md, FRONTEND.md and specs/, compare them with src/, and write a prioritized list of small tasks to plan/IMPLEMENTATION_PLAN.md; plan only, do not implement anything. Build mode: read plan/progress.md first, pick the single most important task, implement it, run every quality gate, commit only when they pass, then update the plan and plan/progress.md.

  5. 5

    Ворота якості і hook

    Set up the quality gates: npm scripts for lint (with jsx-a11y rules), typecheck, build and test:e2e; Playwright tests with axe for accessibility, screenshots at 320, 375, 768, 1024, 1440 and 1920 px, a console-error check and a broken-link check. Add a Stop hook in .claude/settings.json that runs typecheck and lint and sends any failure back to you. Then make each gate fail once on purpose and show me the output, so I know it works.

  6. 6

    Три скіли

    Use skill-creator to create three skills in .claude/skills: build-page (turns a spec from specs/pages into a page that uses our tokens), frontend-qa (runs every quality gate and reports problems in plain English with screenshots, most important first) and client-handoff (prepares README, .env.example and HANDOFF.md). None of them may fix, publish or merge anything without my OK.

    Більше ідей для скілів є на карті фронтенду, у розділі «Перевірки, які варто перетворити на скіли».

Що це, головне і що брати нам

Що це

Коротка ідея-нотатка, яку автор пропонує просто скинути своєму агенту. Звична робота з документами виглядає так: завантажив файли, поставив питання, модель шукає шматки і відповідає. Щоразу з нуля, нічого не накопичується. Карпаті пропонує інакше: агент веде вікі — набір звʼязаних markdown-сторінок, які він сам пише і оновлює з кожним новим джерелом. Ти читаєш, він пише.

Головне

  • Три шари: сирі джерела (їх ніхто не змінює), вікі (її пише тільки агент) і схема — файл правил на кшталт CLAUDE.md, який пояснює агенту, як вікі влаштована і що робити.
  • Три дії: додати джерело (агент читає, обговорює з тобою і оновлює 10–15 сторінок), запитати (гарну відповідь підшити у вікі як нову сторінку) і перевірити (суперечності, застарілі факти, сторінки без посилань).
  • Два службові файли замість пошукової інфраструктури: index.md — каталог усього, log.md — хроніка змін.
  • Людина курує джерела і ставить питання. Агент робить бухгалтерію, через яку люди кидають вікі: перехресні посилання, оновлення, узгодженість.

Для нас. Наш AGENTS.md — це та сама «схема»: правила, які агент виконує без нагадувань. І та сама логіка поділу: людина — рішення і смак, агент — рутина.

agents.md · відкритий формат, Agentic AI Foundation (Linux Foundation)

AGENTS.md: README для агентів

Що це, головне і що брати нам

Що це

Простий відкритий формат: один markdown-файл AGENTS.md у корені репозиторію, де записано все, що агенту треба знати про проєкт. README.md — для людей: про що проєкт і як почати. AGENTS.md — для агентів: як зібрати, як перевірити, які домовленості, чого не робити. Його читають понад 60 тисяч відкритих проєктів і десятки агентів: Codex, Cursor, Copilot, Gemini CLI, Jules, Devin, Factory, Zed, Warp та інші.

Головне

  • Обовʼязкових полів немає: звичайний markdown з будь-якими заголовками. Популярні розділи: огляд проєкту, команди збірки й тестів, стиль коду, правила для PR, безпека.
  • Якщо перелічити команди перевірки, агент сам їх запускає і виправляє помилки, перш ніж сказати «готово».
  • У великому репозиторії файлів може бути кілька: агент читає найближчий до файла, який редагує. Пряме прохання в чаті важливіше за будь-який файл.
  • Це живий документ: пиши все, що сказав би новому колезі в перший день, і оновлюй, коли правила змінюються.
  • Формат виріс зі спільної роботи OpenAI Codex, Amp, Jules, Cursor і Factory, тепер його веде Agentic AI Foundation під Linux Foundation, тож він не належить одному продукту.

Для нас. Усі наші правила живуть у AGENTS.md, а CLAUDE.md лише відсилає до нього. Тож Claude Code, Codex, Cursor і Copilot працюють за одним і тим самим файлом: одні правила на всіх агентів.

SDD: від ідеї до злитого PR по прямій лінії

Що це, головне і що брати нам

Що це

Плагін для Claude Code з 23 навичками, які ведуть фічу від одного речення до перевіреного коду в PR. Кроки йдуть по прямій: описати → уточнити → спроєктувати → розбити на задачі → реалізувати → перевірити → відправити. Кожен крок пише файл, який читає наступний, і відмовляється працювати, якщо попереднього файла немає. Пропустити щось випадково не вийде.

Головне

  • Навички сократичні: ставлять питання і йдуть з тобою по рішеннях, а не вивалюють стіну тексту. Глибина розпитувань налаштовується: easy, medium, hard.
  • Для інтерфейсів є окремий дизайн-конвеєр: design-system (канон: токени, компоненти, інструмент), ux-flows (потоки користувача) і screens — кожен екран у кожному стані: звичайний, завантаження, порожній, помилка.
  • implement працює через TDD: спочатку тест, який падає, потім мінімальний код, перевірка, коміт на кожну задачу.
  • review — незалежна перевірка всієї зміни проти опису. ship запускає фічу по-справжньому, пише changelog і відкриває PR. Злиття в main лишається за людиною.
  • Утиліти на будь-який момент: словник термінів, розбір бага (відтворити → тест → мінімальне виправлення), дорожня карта.

Для нас. Це доросла версія того, що ми робимо руками: спершу домовитися, що будуємо, потім код. «Екран у всіх станах» — саме те, що дизайнер має описати до того, як з'явиться перший рядок.

GitHub · github/spec-kit

Spec Kit: специфікація, яка стає кодом

Що це, головне і що брати нам

Що це

Відкритий інструментарій від GitHub для роботи з будь-яким AI-агентом (понад 30 підтримуваних). Головна думка: десятиліттями код був головним, а описи — тимчасовими риштуваннями. Spec Kit перевертає це: специфікація стає виконуваною, з неї народжуються план, задачі і код.

Головне

  • Кроки: constitution — принципи проєкту, один раз; specify — що і навіщо, без технологій; plan — як, з технологіями; tasks; implement; converge — звірити код з описом і додати задачі на те, чого не вистачає. Повторювати, доки не «зійшлося».
  • Розширення для типових ситуацій: bug (оцінити → виправити → перевірити) і assess — оцінка ідеї до коду: збір → дослідження → визначення → варіанти → рішення «робимо / уточнити / не робимо».
  • Налаштування під команду: extensions додають нові команди, presets змінюють формат і термінологію (аж до іншої мови), bundles збирають готовий набір під роль: продакт, аналітик, безпека, розробник.
  • Філософія: намір і «що» раніше за «як»; уточнення кількома кроками замість одного великого промпта.

Для нас. Constitution — це наш AGENTS.md. Assess — спосіб не будувати те, що не потрібне. Converge — звірити результат з домовленістю, а не з відчуттям «начебто готово».

Superpowers: навички, які спрацьовують самі

Що це, головне і що брати нам

Що це

Методологія розробки для агентів у вигляді набору навичок. Щойно агент бачить, що ти щось будуєш, він не кидається писати код: спершу питає, що ти насправді хочеш, показує дизайн частинами, які можна прочитати, і лише після твого «так» складає план і береться за роботу. Навички вмикаються автоматично, нічого спеціально викликати не треба.

Головне

  • Базовий цикл: brainstorming (уточнити ідею) → окрема гілка → план, написаний так, щоб його виконав «завзятий джуніор без смаку і контексту»: точні файли, код, перевірки → окремий субагент на кожну задачу з двоетапним ревʼю → TDD: тест падає, мінімальний код, тест проходить → ревʼю → злиття або PR.
  • systematic-debugging: чотири фази і залізне правило «без кореневої причини — без виправлень». Три невдалі спроби поспіль означають, що проблема в архітектурі, а не в рядку коду.
  • verification-before-completion: спершу докази, потім слово «готово».
  • Філософія: тести спершу, процес замість вгадування, простота як мета, докази замість заяв.

Для нас. Саме ці навички працюють у цьому репозиторії: брейншторм перед лого, системний пошук причини, коли зникала музика. Це відповідь на питання «чому Claude питає, а не робить одразу».
