# Spec Kit: специфікація, яка стає кодом

**Джерело:** GitHub, репозиторій github/spec-kit — https://github.com/github/spec-kit/blob/main/README.md
**Формат оригіналу:** README відкритого інструментарію з CLI `specify` і командами для AI-агентів, англійською. Проєкт відзначив рік і випуск 1.0.0.
**Для кого цей переказ:** UX/UI дизайнери, які роблять дизайн у коді через Claude і не є програмістами.

## Що це простими словами

Десятиліттями код був головним, а специфікації — тимчасовими риштуваннями, які викидали, щойно починалась «справжня робота». Spec-Driven Development перевертає це: **специфікація стає виконуваною** — з неї народжуються план, задачі і робочий код, а не просто натяк на них.

Spec Kit — відкритий набір інструментів від GitHub, який дає готовий процес розробки від специфікації для **будь-якого AI-агента** (понад 30 інтеграцій: Copilot, Claude Code, Codex, Cursor та інші). Процес можна розширювати і підлаштовувати під команду чи цілу організацію.

## Основний цикл

Після встановлення агент отримує набір команд:

0. **constitution** — один раз на проєкт: принципи і правила розробки (якість коду, тести, послідовність UX, продуктивність). Далі всі кроки на них спираються.
1. **specify** — описати, **що** і **навіщо** будуємо, без технологій. Приклад з README: застосунок для фотоальбомів, згрупованих за датою, які можна перетягувати; фото в альбомі показуються плиткою.
2. **plan** — **як** будуємо: технології й архітектура. Приклад: Vite, мінімум бібліотек, звичайні HTML/CSS/JS, метадані в локальній базі.
3. **tasks** — план розбивається на конкретні задачі.
4. **implement** — агент виконує задачі і будує фічу за планом.
5. **converge** — звірити код зі специфікацією, планом і задачами; чого не вистачає — додати як нові задачі. Кроки 4 і 5 повторюють, доки не буде «Converged» — зійшлося.

Додаткові команди для якості: **clarify** — уточнити недоописані місця перед планом; **analyze** — перевірити узгодженість і покриття між документами перед реалізацією; **checklist** — контрольні списки якості вимог, «юніт-тести для тексту».

## Розширення для типових ситуацій

- **Баги.** Ризиковано, коли агент стрибає від скарги до патча без перевірки діагнозу. Розширення `bug` дає повторюваний цикл: **оцінити → виправити → перевірити**, з документуванням від кореневої причини до підтвердження.
- **Оцінка ідеї.** Гарні ідеї заслуговують на докази до того, як у них вкладатися. Розширення `assess` веде від сирої ідеї до рішення **робимо / потрібно уточнити / не робимо** через кроки: збір → дослідження за і проти → визначення проблеми, цілей і метрик → варіанти рішення з компромісами → рішення. Якщо «робимо», ідея передається в specify.

## Налаштування під команду

- **Extensions** — додають нові команди і можливості: інтеграція з Jira, ревʼю після реалізації, діагностика здоров'я проєкту.
- **Presets** — змінюють, як працює наявне: формат специфікацій, термінологія, обов'язкові перевірки безпеки, порядок «тести спершу», навіть повна локалізація процесу іншою мовою. Пресети можна накладати один на інший за пріоритетом.
- **Bundles** — готовий набір розширень і пресетів під роль: продакт-менеджер, бізнес-аналітик, дослідник безпеки, розробник. Одна команда — і вся роль налаштована.
- Локальні перекриття для одноразових правок в окремому проєкті.

## Філософія

- Розробка від наміру: «що» до «як».
- Багаті специфікації з огорожами і принципами організації.
- Багатокрокове уточнення замість генерації коду одним промптом.
- Опора на здатність сучасних моделей розуміти специфікації.

Проєкт «їсть власну їжу»: команда Spec Kit розвиває Spec Kit через Spec Kit, особливо для великих змін.

Три фази застосування: з нуля (greenfield), творчий пошук (кілька паралельних реалізацій з різними технологіями та UX-патернами), розвиток існуючого (brownfield: додавати фічі, модернізувати старе).

## Терміни простими словами

- **Constitution** — принципи проєкту, записані один раз; аналог нашого CLAUDE.md.
- **Specify / plan / tasks / implement** — що, як, на які кроки, зроби.
- **Converge** — звірити результат з домовленістю і доробити, доки не зійдеться.
- **Extension / preset / bundle** — додати нове / змінити наявне / готовий комплект під роль.
- **Greenfield / brownfield** — новий проєкт / існуючий проєкт.

## Як це стосується дизайнерів, які роблять дизайн у коді через Claude

- Constitution — це наш `CLAUDE.md`: правила про гілки, токени, компоненти, які агент виконує сам.
- specify без технологій — саме та частина, яку дизайнер може написати найкраще: для кого, що має статися, як зрозуміємо, що готово.
- assess допомагає не будувати те, що не потрібне: спершу докази, потім код. Для дизайну це «проблема → метрики → варіанти → рішення» ще до макета.
- converge — звірити результат із домовленістю, а не з відчуттям «начебто готово». Для нас це скриншоти в PR і перегляд UI kit.
- Пресети показують, що процес — теж дизайн: його можна перекласти українською і підлаштувати під команду.

## Питання для обговорення

1. Чому «специфікація стає виконуваною» — це перевертання звичного порядку?
2. Яку частину циклу (constitution, specify, plan) має писати дизайнер, а яку розробник?
3. Що дає повторення implement → converge, доки не зійдеться?
4. Коли ідею варто пропустити через assess, а коли просто зробити прототип?
5. Що б ви поклали в constitution своєї дизайн-команди?
