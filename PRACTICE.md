# Тренування: двоє дизайнерів, один репозиторій

Чотири вправи на 1–2 години. Потрібні: двоє людей (A і B), у кожного — Claude Code і цей репозиторій. Усі дії робимо через Claude: ти кажеш, що потрібно, він виконує git-команди і пише код. Команди наведені, щоб було зрозуміло, що відбувається під капотом.

## 0. Підготовка (10 хв)

Кожен окремо:

> «Клонуй `https://github.com/eleken-git/design-process-help.git`, встанови залежності і запусти проєкт»

```bash
git clone https://github.com/eleken-git/design-process-help.git
cd design-process-help
npm install
npm run dev        # http://localhost:5173
```

Відкрий три екрани: `#/dashboard`, `#/settings`, `#/ui-kit`. Унизу кожного екрана — підказка, де лежить його код і як назвати гілку.

Ролі: **A — Dashboard**, **B — Settings**. Ревʼюєте одне одного.

## 1. Паралельні екрани без конфліктів (20 хв)

Мета: відчути, що різні папки = нуль конфліктів.

| | A | B |
|---|---|---|
| Гілка | «Почни нову задачу: гілка `feat/dashboard-churn-card` від свіжого `main`» | «Почни нову задачу: гілка `feat/settings-security` від свіжого `main`» |
| Задача | «На Dashboard додай четверту картку статистики “Нові підписки”, значення 96, дельта +15%» | «У Settings додай картку “Безпека” з перемикачем “Двофакторна автентифікація” та описом» |
| Зберегти | «Закоміть як `dashboard: картка нових підписок` і запуш гілку» | «Закоміть як `settings: картка безпеки` і запуш гілку» |
| PR | «Відкрий PR за шаблоном, додай скриншоти до/після» | те саме |
| Ревʼю | ревʼює PR B на GitHub → Approve | ревʼює PR A → Approve |
| Merge | той, хто ревʼює, натискає **Squash and merge** | |

Перевір себе: у `main` обидві зміни, `npm run dev` показує і нову картку, і нову секцію. Конфліктів не було, бо `src/screens/dashboard/` і `src/screens/settings/` не перетинаються.

Після merge обоє: «Підтягни `main` у мою гілку» або просто «Перейди на `main` і оновись».

## 2. Спільний компонент правильно (25 хв)

Мета: змінити компонент так, щоб чужий екран не змінився.

Сценарій: A хоче на Dashboard бейдж жовтого кольору для подій «увага». У `Badge` немає такого `tone`.

A:
1. «У гілці Dashboard `Badge` не чіпаємо. Закоміть поточне і почни гілку `ds/badge-tone-attention` від свіжого `main`»
2. «Додай у `Badge` новий `tone="attention"` на основі токена `--color-attention`. Дефолт `neutral` не змінюй. Покажи новий варіант на `#/ui-kit`»
3. «Перевір `npm run typecheck && npm run build`, закоміть як `badge: tone attention`, запуш і відкрий PR зі скриншотом `#/ui-kit`»

B: ревʼює PR за 15 хвилин. Питання, на які треба відповісти «так»: дефолт не змінився? інші tone виглядають так само? новий варіант є на `#/ui-kit`? → Approve → Squash and merge.

Обоє: «Підтягни `main` у мою гілку». A використовує `<Badge tone="attention">` на Dashboard. У B на Settings нічого не змінилося.

Перевір себе: відкрий `#/settings` — бейджі команди виглядають як раніше.

## 3. Конфлікт навмисно (15 хв)

Мета: побачити конфлікт у безпечних умовах і розвʼязати його.

Обоє одночасно, кожен у своїй гілці (`feat/brand-a` і `feat/brand-b`):

- A: «У `src/App.tsx` зміни назву продукту `Nimbus` на `Nimbus Cloud`»
- B: «У `src/App.tsx` зміни назву продукту `Nimbus` на `Nimbus Pro`»

A першим відкриває PR і зливає. B: «Підтягни `main` у мою гілку» → Claude повідомляє про конфлікт у `src/App.tsx` і показує обидві версії рядка. B каже, яку лишити (або пропонує третю), Claude завершує merge, пушить, відкриває PR.

Перевір себе: у `main` одна назва, історія обох PR збереглась. Запамʼятай: конфлікт — це не поломка, це питання «чия версія рядка».

## 4. Breaking change за процедурою (20 хв, просунуте)

Мета: змінити дефолт або перейменувати проп і нікого не зламати.

Сценарій: команда вирішила, що `variant="secondary"` у `Button` має називатися `variant="outline"`.

1. Спершу у чаті: «Перейменовую secondary → outline, зачепить Dashboard і Settings». Другий підтверджує.
2. «Гілка `ds/button-outline` від свіжого `main`. Перейменуй `variant='secondary'` на `'outline'` у `Button`, знайди всі використання в проєкті і онови їх у цьому ж коміті. Оновити `#/ui-kit`»
3. `npm run typecheck` — саме він знайде пропущені місця.
4. PR зі скриншотами `#/ui-kit`, `#/dashboard`, `#/settings`. Ревʼю обох. Squash and merge.

Перевір себе: `grep -rn "secondary" src` не знаходить нічого в екранах.

## Що робити, коли щось пішло не так

| Ситуація | Скажи Claude |
|---|---|
| Закомітив у `main` випадково | «Перенеси мій останній коміт у нову гілку `feat/…` і поверни `main` до стану origin» |
| Почав правити спільний компонент у `feat/` гілці | «Винеси зміни в `src/components` в окрему гілку `ds/…` від свіжого `main`» |
| Гілка «розʼїхалась» з `main` | «Підтягни `main` у мою гілку і розкажи, що змінилось» |
| Не розумію, що зараз у репозиторії | «Покажи, на якій я гілці, що змінено і що ще не запушено» |
